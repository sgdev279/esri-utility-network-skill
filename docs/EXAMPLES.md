# Worked examples

Three real questions, each with the exact details a consultant would be given, and what this repo actually produces for them. The command output and JSON below were captured by running the scripts in this repo. See [TESTING.md](TESTING.md) for how the answers were checked and where they fell short.

## 1. "Apply Asset Package fails when I add gas to our water UN"

> Pro 3.5, Enterprise 11.3 (PostgreSQL). `WaterUN` in dataset `WaterDistribution` already has the `Water` domain network. Applying the Gas Foundation with *Domain networks to apply* = Gas. Two maps open (Editing, Publishing). Connected to the database as `gis_editor` (UN owner is `wateradmin`); portal login `jsmith` (portal UN owner is `wateradmin`); current version `wateradmin.crew1`; topology is enabled because dispatch traces all day.

What the skill does with it (from `pro-help/08` and `pro-help/10`): checks the setup against Esri's prerequisites and finds **five** violations, not one, so fixing a single one just moves the error.

| Requirement | This setup | |
|---|---|---|
| All maps closed | Editing and Publishing open | fails |
| Network topology disabled | enabled | fails |
| Connected as the **database** UN owner | `gis_editor`, owner is `wateradmin` | fails |
| Signed in as the **portal** UN owner | `jsmith`, owner is `wateradmin` | fails |
| Connected to DEFAULT | `wateradmin.crew1` | fails |
| Pro version matches the dataset version | Pro 3.5 with a v7-or-lower dataset | passes; check the dataset version |

Then the order: backup and warn dispatch, close maps, sign in as `wateradmin` and connect as `wateradmin` on DEFAULT, disable topology, apply **only** Gas, post-process and re-enable topology. Applying Gas does **not** wipe Water: Apply Asset Package is additive, it never removes or modifies existing properties.

## 2. "Write the REST request for an isolation trace on `crew1.outage`"

> Water main `{8F2A6C1E-4B7D-4E1A-9C55-2D0F7A1B3E90}`, break at the midpoint. Isolating valves carry the category `Isolating`; network attribute `Operable` = 1 means operable. Domain `Water`, tier `Pressure`. Branch version `crew1.outage`, and someone else may have it open. Which service connections lose water? What if it returns zero elements?

The request body ([`examples/isolation-trace/request.json`](../examples/isolation-trace/request.json)):

```json
{
  "f": "json",
  "gdbVersion": "crew1.outage",
  "traceType": "isolation",
  "traceLocations": [
    {
      "traceLocationType": "startingPoint",
      "globalId": "{8F2A6C1E-4B7D-4E1A-9C55-2D0F7A1B3E90}",
      "percentAlong": 0.5
    }
  ],
  "traceConfiguration": {
    "domainNetworkName": "Water",
    "tierName": "Pressure",
    "includeBarriers": true,
    "includeIsolated": true,
    "validateConsistency": true,
    "filterBarriers": [
      {"name": "Category", "type": "category", "operator": "includesTheValues",
       "value": "Isolating", "combineUsingOr": false, "isSpecificValue": true},
      {"name": "Operable", "type": "networkAttribute", "operator": "equal",
       "value": "1", "combineUsingOr": false, "isSpecificValue": true}
    ],
    "filterScope": "junctions"
  },
  "resultTypes": [
    {"type": "elements", "includeGeometry": false,
     "includePropagatedValues": false, "includeDomainDescriptions": true}
  ]
}
```

Checked with the validator:

```console
$ python scripts/build_trace_request.py --check examples/isolation-trace/request.json
OK: no problems found
```

Things the answer gets right that are easy to get wrong:

- The main is a line, so the start uses `percentAlong: 0.5` and **no** `terminalId`. A location with neither is silently ignored by the service.
- The isolating valves go in **`filterBarriers`** (category `Isolating` AND `Operable = "1"`), values as strings.
- **No `sessionId`.** It is only for a client that holds the exclusive edit session on the version. Someone else editing `crew1.outage` does not require it; the trace reads the saved state and will not see their unsaved edits.
- Trace elements carry **codes**, not names: `networkSourceId`, `assetGroupCode`, `assetTypeCode`. Find the service connection codes in `queryDataElements`.
- `includeIsolated: true` is what returns the affected features, so the service connections appear.

The same validator on a request with typical mistakes ([`request.broken.json`](../examples/isolation-trace/request.broken.json)):

```console
$ python scripts/build_trace_request.py --check examples/isolation-trace/request.broken.json
PROBLEMS:
 - sessionId 'not-a-guid' must be a GUID in braces, generated by your client
 - traceLocations[0]: percentAlong must be 0-1
 - traceLocations[1] ({5B3C0E1A-77D2-4C0B-8A11-3E9D2F6A4B10}): needs terminalId (junction) or percentAlong (edge) — the service silently ignores it otherwise
 - isolation trace: domainNetworkName and tierName are normally required
 - traceConfiguration: unknown key 'tierNam' (typo? check rest-api/08)
 - filterBarriers[0]: name is required (network attribute name, or Category for category conditions)
 - filterBarriers[0]: operator 'equals' not valid
WARNINGS:
 - sessionId is only needed when THIS client holds the exclusive edit session on the version; for a read-only trace on a version someone else is editing, omit it
```

Exit status is 1. Warnings never change the exit status.

## 3. "Our dirty areas show Status 1, 2, 9, 8 and 40; validate says success but 8 and 40 are still there"

> After loading 46k features into a branch version: Status 1 x 41,220; Status 2 x 130; Status 9 x 312; Status 8 x 5; Status 40 x 18.

```console
$ python scripts/decode_dirty_status.py 1 2 9 8 40
1: feature inserted or updated  [edit only]  ->  No error. Just validate network topology over this area; validate clears it.
2: feature deleted  [edit only]  ->  No error. Just validate network topology over this area; validate clears it.
9: feature inserted or updated; feature error  [edit + error]  ->  Validate will evaluate it. If the feature still violates a rule the error bit stays and the row becomes error-only; fix the cause by editing, then validate.
8: feature error  [error only]  ->  Validate will IGNORE this row. Find the cause (Error Inspector: Network Source ID, Feature GUID, error code), fix it by EDITING the feature, rule or subnetwork definition, save, then validate.
40: feature error; subnetwork error  [error only]  ->  Validate will IGNORE this row. Find the cause (Error Inspector: Network Source ID, Feature GUID, error code), fix it by EDITING the feature, rule or subnetwork definition, save, then validate. Subnetwork error: after the fix, run Update Subnetwork; the subnetwork stays Invalid until it updates cleanly.
```

The key fact (Esri, Dirty areas page): **Validate Network Topology only evaluates dirty areas that carry an edit bit (1, 2 or 4).** Status 8 and 40 are error-only rows, so validate ignores them, and re-running it does nothing. Edit the feature (or the rule, or the subnetwork definition) to fix the cause; the edit adds an edit bit and the next validate can clear it. For 40 (bit 32, subnetwork error), run Update Subnetwork afterwards: the subnetwork stays Invalid until it updates cleanly. "Success" only means the job ran.
